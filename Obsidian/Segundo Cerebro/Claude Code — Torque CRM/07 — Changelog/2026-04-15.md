# Changelog — 2026-04-15

## Adicao do Agente Security ao time

Time autonomo expandiu de 9 para 10 agentes. Novo agente dedicado a seguranca com poder de veto em deploys sensiveis.

### Motivacao

Pre-analise do codebase identificou superficie critica sem dono:

- 49 edge functions com `verify_jwt = false` sem linter
- 131+ migrations com 20+ refixes de RLS
- Rate limit em memoria + fallback `allowed: true`
- `rls-org-isolation.test.ts` skipado em CI
- 7 integracoes externas sem rotacao de secrets
- LGPD sem mapeamento formal de PII

Com ~30 orgs crescendo e time pequeno (CTO + junior), custo de incidente >> custo operacional do agente.

### Triggers do novo agente

Conductor invoca Security quando task toca: auth, permissoes, RLS, policies, secrets, CORS, webhook, pagamento (Asaas), OAuth, PII, LGPD, master_users, service_role, `supabase/config.toml`, `.github/workflows/`, Dockerfile.

Ordem em features sensiveis:
```
Architect → Security (threat model) → DBA → Backend → Security (RLS + auth review) → Frontend → QA → Security (final gate) → Infra
```

### Poder de veto

Security pode bloquear merge/deploy em:
- SAST, SCA ou secrets scan falhando
- RLS policy nova sem teste pgTAP
- Edge function publica sem `validateAuth()` testado
- Mudanca em pagamento/auth/master sem threat model
