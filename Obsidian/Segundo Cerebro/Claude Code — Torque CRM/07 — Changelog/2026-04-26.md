# 2026-04-26 — Fix createInstance no whatsapp-api-proxy (Evolution)

## Bug

Frontend ao criar instância WhatsApp recebia:

```
whatsapp-api-proxy: Edge Function returned a non-2xx status code
```

Causa raiz: branch `createInstance` inseria `provider: "uazapi"` e chamava `getWhatsAppProvider(newRow)` logo após o INSERT. Factory para Uazapi faz RPC `get_uazapi_credentials` para montar `UazapiProvider` com token por-instância. Token só é gravado pelo próprio `provider.createInstance()` (via `set_uazapi_credentials`) → RPC vazia → throw `"No uazapi credentials found for instance <id>"` → 500.

Bug duplo:
1. Provider errado: sistema opera com **Evolution**, não Uazapi (Uazapi é roadmap futuro/migração).
2. Bootstrap: factory Uazapi exigia credencial que só existe após o passo que ela deveria habilitar.

## Fix

Arquivo: `supabase/functions/whatsapp-api-proxy/index.ts`

1. Insert agora usa `provider: "evolution"` (era `"uazapi"`).
2. `EvolutionProvider` instanciado direto na branch `createInstance` — Evolution usa `EVOLUTION_API_KEY` global, sem credencial por-instância.
3. Cleanup do row órfão se `provider.createInstance()` falhar — evita que a constraint `UNIQUE(organization_id, instance_name)` bloqueie retries com mesmo nome.

Demais branches (getStatus, connectQR, deleteInstance, sendText, etc.) continuam usando a factory `getWhatsAppProvider` — para Evolution ela só lê `instance.instance_name` do row, sem RPC.

## RC-cancel — Copilot Cancel-on-Disable (v1)

Adendo à RC v1 mesmo dia. Resolve UX recorrente: user desativa copilot mid-conversa e copilot ainda envia mensagem que estava na fila/setTimeout.

**Decisões CTO** (4 perguntas confirmadas):
- Cancelar tudo no meio (não termina o que começou).
- NÃO salva reply cancelada em `conversation_messages` (delete pós-cancel).
- Log em `runtime_logs` (`module='copilot'`, `action='copilot_canceled'`).
- Liga pra todas as orgs imediatamente (sem flag).

**Janelas de delay cobertas:**

| Janela | Onde | Status pré-RC | Status pós-RC |
|---|---|---|---|
| 1. Batch wait pré-LLM | `sz-chat-webhook` (`response_delay_seconds`) | já protegido (re-check pós-batch, linha 498) | mantido |
| 2. LLM call (~5-30s) | `agent-message/index.ts` | sem proteção | gate pós-LLM (skip delivery + delete assistant message) |
| 3. Natural messaging chunks | `sendSzChatResponse`, `outbound-sender`, `followup-sender` | sem proteção | gate per-chunk (break loop) |

**Implementação:**

- `_shared/copilot/cancellation.ts` — novo módulo:
  - `isCopilotCanceled(supabase, organizationId, phone)` lê `phone_ai_preferences.ai_disabled` (fonte de verdade) com fallback `leads.ai_disabled` (lead mais recente). Phone normaliza via `normalizeBrazilianPhone`. Fail-open em erro DB.
  - `logCopilotCancellation({ organizationId, gate, leadId?, conversationId?, phone?, chunksSent?, chunksTotal?, source? })` fire-and-forget.

- `agent-message/index.ts` (linha ~107):
  - Após `engine.processMessage`, antes de retornar response.
  - Se cancelado: `DELETE FROM conversation_messages WHERE conversation_id=X AND role='assistant' AND content=Y AND created_at >= now()-60s`.
  - Retorna `{ skipped: true, reason: 'ai_disabled_during_processing', canceled_gate: 'post_llm' }` 200 OK.

- `sz-chat-webhook/index.ts` `sendSzChatResponse`:
  - Aceita `supabase` opcional; se passado, checa per-chunk antes do `sendViaSzChat`.
  - Cancelado mid-loop: `break`, `logCopilotCancellation({ gate: 'sz_chat_chunks', chunksSent, chunksTotal })`.
  - Cobre ambos paths: smartSplit (natural) + classic split (fallback).

- `_shared/outbound-sender.ts` `sendText`:
  - Per-chunk gate dentro do for loop, após o setTimeout do delay.
  - Retorna `{ ok, canceled, chunksSent, chunksTotal }`.
  - Caller atualiza `outbound_dispatch_log.status='canceled'` com `trigger_reason.canceled_mid_send=true`.

- `_shared/followup-sender.ts`:
  - Per-chunk gate, `break` em cancel.
  - Se cancelado antes de qualquer chunk sair → retorna `{ success: false, error: 'canceled_before_send' }`.

**Testes** (`tests/unit/copilot/cancellation.test.ts`): 8 testes — fonte de verdade, fallback, default, phone vazio, org vazio, phone inválido, prioridade phone_ai_preferences sobre leads. **8/8 passed.**
