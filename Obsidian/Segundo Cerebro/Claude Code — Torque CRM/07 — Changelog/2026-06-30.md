# 2026-06-30

## Mudanças

- **pipelines / kanban**: contagem das colunas do kanban agora reflete os filtros aplicados (antes mostrava sempre o total). Todos os filtros client-side dos 3 funis sistema (whatsapp/confirmação/propostas) foram empurrados pros RPCs de paginação. Bug reportado: org Basic4u, coluna Perdido=21; ao filtrar origem=site ficavam 10 cards mas o badge seguia 21.

## Causa raiz

- Badge da coluna (`DraggableKanbanBoard.tsx:105`) renderiza `column.totalCount`, vindo de `get_pipeline_stage_counts`, que só conhecia search/responsável/tags.
- Origem, período, agendado, urgência, calor, prioridade, time-bucket e status rodavam client-side (`filterItemsLocal`) **depois** da paginação → encolhiam os cards mas não o `totalCount`. 2º problema: filtro client só via a página carregada (20/etapa).

## Arquivos tocados

- `supabase/migrations/20270101000400_kanban_filters_server_side.sql` — DROP+CREATE de `get_pipeline_page` e `get_pipeline_stage_counts` com ~16 params genéricos novos (origens[], faixas rating/calor, ranges meeting/period, urgência, status[], overdue, agendado). `SECURITY INVOKER` + `search_path=''` + full-qualify. `l.origin::TEXT` (enum). Período status-dependente via `p_closed_status_keys` (espelha `isPropostaInPeriod`).
- `src/modules/pipelines/hooks/model/usePaginatedPipeline.ts` — `PaginatedFilters` estendida; `sharedRpcParams` (1 fonte de verdade pros 2 RPCs); query keys via `filtersKey` (refetch em qualquer dimensão).
- `src/modules/pipelines/lib/kanbanFilterParams.ts` (novo) — mappers puros `priorityBandToRating`/`calorBandToBounds` + constantes de status.
- `src/modules/pipelines/pages/{PipeWhatsapp,PipeConfirmacao,PipePropostas}.tsx` — montam `filters`, removem `filterItemsLocal`; confirmação traduz time-bucket → range/overdue (`timeParams`). Imports mortos removidos (`leadsWithSchedule`, `matchesResponsibleFilter` em confirmação — server 4-field já dominava, client 9-field era no-op).
- `tests/unit/kanban-filter-params.test.ts` (novo) — 12 testes de parity das bandas + partição 0..10.

## Decisões

- **Filtro server-side completo** (escolha do CTO sobre fix rápido/frontend-only): conta + paginação sempre consistentes, mata a classe de bug. Princípio: client traduz banda/bucket/timezone → params genéricos; RPC só aplica predicado SQL. Mantém defaults (`rating||0`, `calor??5`) e tz no client.
- Param `NULL` = filtro desligado (curto-circuita; custo zero quando inativo).
- Melhoria de parity intencional: cards de confirmação **sem** `meeting_date` agora são excluídos dos buckets today/tomorrow/week (o client deixava passar — quirk).

## Verificação

- Build + lint (0 errors) + 12 testes verdes. Suíte cheia tem 71 falhas **pré-existentes** (copilot/knowledge-retriever etc.), nenhuma nos arquivos tocados.
- Lógica dos predicados validada read-only contra PROD (Basic4u): origem=site→Perdido 10 (era 21), calor default→warm 93, período CASE 27, scheduled EXISTS sem erro.
