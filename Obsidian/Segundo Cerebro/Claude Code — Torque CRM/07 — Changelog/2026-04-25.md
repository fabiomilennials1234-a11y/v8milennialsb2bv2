# 2026-04-25 — Fix disparos WhatsApp duplicados (race condition lead-webhook)

## Bug reportado

Cliente Basic4u reportou que disparos de WhatsApp do workflow "Automação | Qualificação inicial" estavam chegando aos leads em **dobro**. Investigação confirmou impacto em outras 8 orgs (Milennials, Vanilla Brasil, The Good Balloon, REALSC, BV, Bella Itália, Drink Express, Safe Clear). Total: 142 leads duplicados, 9 orgs afetadas.

## Root cause

**Race condition no `lead-webhook` com Meta Lead Ads retry.**

Cadeia da falha:
1. Meta envia webhook do lead, retry agressivo se não recebe 200 em < 1s → 2 chamadas concorrentes ao endpoint
2. `getOrCreateLead` em [lead-service.ts:140-158](../../../../supabase/functions/_shared/lead-service.ts) faz `SELECT WHERE normalized_phone = X` — ambas chamadas retornam vazio (lead ainda não existe)
3. Ambas chamadas fazem INSERT na `leads` — sem UNIQUE constraint, ambos passam → 2 leads idênticos criados em **18-60ms** de diferença
4. Postgres trigger `lead_created` dispara `workflow_executions` 2x (1 por lead novo)
5. Workflow executa 2x → mensagens WhatsApp dobradas

Catch de race em [lead-service.ts:230-275](../../../../supabase/functions/_shared/lead-service.ts) (handle `23505 unique_violation` + retry-search) era código defensivo, mas **a constraint não existia** → catch nunca disparava.

### Por que constraint estava faltando

Migration original [20260130100000_lead_phone_centralization.sql:151-153](../../../../supabase/migrations/20260130100000_lead_phone_centralization.sql) tinha o `CREATE UNIQUE INDEX` **comentado** com nota "habilitar após resolver duplicatas". Nunca foi descomentado.

### Evidência (Basic4u, 7d antes do fix)

```
Maria Clara Prando | 11974744169 | meta_ads | 02:39:14.393873  ← lead 1
Maria Clara Prando | 11974744169 | meta_ads | 02:39:14.453426  ← lead 2 (60ms depois)
```

9 phones com pares dup só na Basic4u. Padrão: gap de 18-60ms entre INSERTs, mesmo nome, mesmo origin (`meta_ads`).

## Fix aplicado

### Migration `20260919000000_merge_duplicate_leads_and_unique_index.sql`

Em transação única:

1. **CTE `_lead_dedupe_map`**: identifica grupos `(organization_id, normalized_phone)` com >1 lead, marca o mais antigo como `canonical_id`
2. **Pre-dedupe** em 8 tabelas com unique constraint envolvendo `lead_id`:
   - `conversation_context_summary`, `conversations`, `lead_scores` (UNIQUE só `lead_id`)
   - `lead_tags` (UNIQUE `lead_id, tag_id`)
   - `lead_custom_field_values` (UNIQUE `lead_id, field_id`)
   - `custom_pipe_entries` (UNIQUE `pipeline_id, lead_id`)
   - `copilot_ab_assignments` (UNIQUE `agent_id, lead_id`)
   - `upsell_clients` (UNIQUE `organization_id, lead_id`)

   Estratégia: deletar row do duplicate se canonical já tem entry equivalente (canonical leva o estado mais antigo)
3. **Re-aponta FKs genericamente** via `information_schema.constraint_column_usage` — pega TODAS as tabelas com FK pra `leads.id` (descobre futuras tabelas automaticamente)
4. **Cancela `workflow_executions`** com status `pending|processing|waiting` que sejam duplicadas (mesmo `workflow_id + lead_id`, mantém a mais antiga) — para disparos em fila
5. **DELETE** dos leads duplicados (canonical preservado)
6. **`CREATE UNIQUE INDEX idx_leads_org_phone_unique`** em `(organization_id, normalized_phone) WHERE normalized_phone IS NOT NULL`

### Resultado

| Antes | Depois |
|-------|--------|
| 6519 leads | 6377 leads |
| 124 grupos dup | 0 dups |
| Sem unique constraint | `idx_leads_org_phone_unique` ✓ |

Validação direta:
```
INSERT INTO leads (..., normalized_phone='11974744169', ...);
ERROR: 23505: duplicate key value violates unique constraint "idx_leads_org_phone_unique"
DETAIL: Key (organization_id, normalized_phone) = (..., 11974744169) already exists.
```

## Por que não muda código backend

Catch de race em [lead-service.ts:230-275](../../../../supabase/functions/_shared/lead-service.ts) já estava pronto — só precisava da constraint pra disparar. Daqui pra frente:
- Meta retry → 2º INSERT bate `23505` → catch executa retry-search → retorna lead canônico → zero impacto user
- Workflow_executions: 1 por lead novo (não 2)
- Disparos WhatsApp: 1x

## Impacto secundário (não tratado, fora do escopo)

Análise inicial levantou H1 (process-outbound-dispatches sem claim atômico) e H2 (loop self-amplifying via `stage_changed` PG trigger após auto-reply do copilot). Ambos são amplificadores possíveis mas com o fix #1 a fonte primária do bug está eliminada — duplicação ms-gap não acontece mais.

Se sintoma persistir após este fix, abrir issue separado:
- H1: criar `claim_outbound_dispatches` RPC com `FOR UPDATE SKIP LOCKED` (similar ao `claim_workflow_executions` já existente)
- H2: adicionar GUC `app.skip_workflow_trigger` ou coluna `pipe_whatsapp.last_changed_by` pra trigger pular auto-reply do copilot

## Comandos pra reproduzir validação

```bash
# Total leads + duplicatas remanescentes
supabase db query --linked --output csv "
SELECT COUNT(*) AS total FROM leads;
SELECT COUNT(*) AS dups FROM (
  SELECT 1 FROM leads
  WHERE normalized_phone IS NOT NULL
  GROUP BY organization_id, normalized_phone
  HAVING COUNT(*) > 1
) sub;
"
# → total=6377, dups=0

# Tentar inserir duplicado
supabase db query --linked "
INSERT INTO leads (organization_id, name, phone, normalized_phone, origin)
VALUES ('163874dd-d05c-4ae2-811a-d6772b05dac5', 'TEST', '+5511974744169', '11974744169', 'meta_ads');
"
# → ERROR: 23505 duplicate key value violates unique constraint "idx_leads_org_phone_unique"
```

## Decisão de arquitetura confirmada

Lead já é entidade global única no schema. Pipes (`pipe_whatsapp`, `pipe_confirmacao`, `pipe_propostas`, `custom_pipe_entries`) são tabelas FK pra `leads.id`. CLAUDE.md documenta: "Lead → tem entradas em pipes (1:N) — um lead pode estar em vários funis simultâneos". Não há lead-por-pipe; a duplicação era acidental (race), não estrutural.
