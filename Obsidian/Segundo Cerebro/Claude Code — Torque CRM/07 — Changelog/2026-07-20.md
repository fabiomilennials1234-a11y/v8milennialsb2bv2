# 2026-07-20

## Mudanças
- **communication / WhatsApp message limits**: `getMessageLimits` agora repassa `organization_id` ao `whatsapp-api-proxy`, espelhando `getStatus`/`connectQR`. Corrige bug funcional multi-tenant: usuário **master** (sem `team_member`) vendo instância de org ≠ `localStorage.selected_org_id` fazia o proxy receber a org errada e devolver **403 cross_tenant** — o widget de limite de mensagens quebrava. Membro comum não era afetado (nunca caía no fallback cross-org). O 403 do proxy estava **correto** (defesa server-side intacta); o defeito era o cliente enviar a org errada.

## Arquivos tocados
- `src/modules/communication/lib/whatsappApi.ts` — `getMessageLimits(instanceId, organizationId?)` passa `organization_id: organizationId` no `callProxy`. 2º param opcional → retrocompat: sem org, `callProxy` mantém o fallback legado (`localStorage.selected_org_id`).
- `src/modules/communication/hooks/useMessageLimits.ts` — `useMessageLimits(instanceId, organizationId?)` repassa a org e inclui `organizationId` na `queryKey` (`["whatsapp_message_limits", instanceId, organizationId ?? null]`) — cache separa por (instância, org).
- `src/modules/communication/components/chat/view/ChatHeader.tsx` — call site A: `useMessageLimits(instanceId ?? null, organizationId)` (prop `organizationId` já existia no componente).
- `src/modules/platform/components/settings/WhatsAppSettings.tsx` — call site B: `MessageLimitsCard` aceita `organizationId?` e o repassa; render passa `organization_id={instance.organization_id}` (org da instância exibida).
- `src/modules/communication/lib/whatsappApi.test.ts` — **novo** (vitest). 3 casos: (1) com org → `organization_id` no body do invoke; (2) sem org e sem localStorage → org ausente (fallback); (3) sem org com `selected_org_id` no localStorage → usa o valor stored. Mocka `supabase.functions.invoke`.

## Decisões
- **Backend/proxy intocado.** O fix só corrige a org que o cliente envia; a validação de tenant server-side continua igual. O `organization_id` enviado é SEMPRE o da instância exibida (`instance.organization_id`) — nunca inventado/ampliado. Membro comum: comportamento inalterado.

## Follow-ups
- **Defeito latente idêntico** em `getStatus`/`connectQR`/`logout` para master: os hooks de instância derivam org de `useCurrentTeamMember` → `null` para master → `callProxy` cai no fallback `localStorage`. Fix estrutural real = **no proxy**: no path master, resolver `callerOrgId` a partir da própria instância para ações instance-scoped (em vez de exigir org do cliente). Recomendado abrir issue separada (não implementado nesta task).
