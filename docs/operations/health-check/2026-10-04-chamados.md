## CHAMADO 1 — Resumo automático de conversas parou de funcionar  ·  Severidade: ALTA

- Serviço: edge function `summarize-conversations-batch` (torque-edge, produção)
- Sentry: https://torquecrm.sentry.io/issues/TORQUE-EDGE-1
- Números: 427 ocorrências, desde 01/10 16:07 UTC, última em 04/10 15:17 UTC (erro ainda ativo). Ninguém reclamou ainda (0 usuários), porque é um processo de fundo.

**O que aconteceu (em português simples)**
Todo o tempo um "robô" roda sozinho e pede ao banco de dados uma lista de conversas de
WhatsApp para resumir (o Oráculo usa esses resumos). O banco está respondendo com erro
nesse pedido, **toda vez**. Resultado: nenhum resumo novo é gerado desde 01/10 e o
robô fica tentando de novo a cada rodada, gerando o alarme.

**Por que não sabemos o motivo exato**
O código joga fora a mensagem real do banco e só mostra "Falha ao reservar conversas
para resumo" (`supabase/functions/summarize-conversations-batch/index.ts:42`).

**Hipóteses (nenhuma confirmada)**
1. A função do banco `claim_conversation_summary_jobs` está quebrada: ela devolve colunas
   com os mesmos nomes (`organization_id`, `lead_id`, `instance_id`) que usa no
   `ON CONFLICT` dentro dela, o que no Postgres costuma dar "column reference is ambiguous"
   (`supabase/migrations/20271019150000_oraculo_conversas_legiveis.sql:225-267`).
2. A migration `20271019150000` não foi aplicada em produção (a função não existe lá).

**Como descobrir (1 minuto, no SQL do Supabase de produção)**
`select * from public.claim_conversation_summary_jobs(1);`
- erro `42702` (ambiguous) → hipótese 1: ajustar a função (qualificar as colunas ou `#variable_conflict use_column`).
- erro `42883` (function does not exist) → hipótese 2: aplicar a migration.
- Em qualquer caso: logar `error.message` em vez de descartá-lo (index.ts:42).

## CHAMADO 2 — Tela de Métricas: erro ao combinar "Ganho x Perda" com recorte "total"  ·  Severidade: BAIXA

- Serviço: torque-web, rota `/metricas` (produção)
- Sentry: https://torquecrm.sentry.io/issues/TORQUE-WEB-1K
- Números: 2 ocorrências, 1 usuário (perfil master, Florianópolis), 02/10 e 03/10. Há replays: https://torquecrm.sentry.io/explore/replays/70d050212f4a41db82fc6042a15bb57e/

**O que aconteceu (em português simples)**
A métrica "Ganho x Perda" só sabe responder de um jeito: dividida por "desfecho"
(ganhou / perdeu). Alguém pediu essa métrica com o recorte "total" (um número só). O banco
recusou, de propósito, para não mostrar uma resposta de outra pergunta
(`supabase/migrations/20270821170000_metric_ganho_perda.sql:80-83`). O usuário viu um
erro em vez do gráfico.

**Hipótese (não confirmada)**
A interface deveria oferecer só `desfecho` para essa métrica
(`classic/src/modules/analytics/lib/metrics-studio-engine-map.ts:121`), mas um card/painel
salvo antes, ou um caminho da UI, ainda manda `total`. Os replays acima mostram o clique exato.

**Próximo passo**: abrir o replay, ver qual card gerou o pedido e corrigir a UI (ou o card salvo). Sem urgência.
